## 一、命令路由：一 URL 一 queue（取代"单活跃页 + 手动激活"）

- 背景：muse.ai 多 tab 准实时同步同一对话；deepseek 经 2026-10-08 用户 live test
  证实同对话双 tab 也是准实时同步（原假设"deepseek 不同步"被证伪）→ 同一块会被
  多个 tab 的 content script 同时抓到 → 重复提交 → 5s 宽限打回。
- 设计：key = 归一化来源 URL（origin + path，去 query/fragment）。
  - 一 URL 一自动执行 queue；不同 URL 各自排队，公平 pump 进串行 host；
  - 同 URL 第二个 tab 的提交按 block id 去重后静默丢弃（无需手动激活页面）；
  - 5s 跨 session busy 打回退役，改为排队。
- 注册表 v1 放扩展侧（按浏览器 profile 隔离）；host 侧本机全局注册表
  （文件锁 + 心跳）记为预留升级点。
- machine_id 正交：管"哪台机器"，URL key 管"哪条对话流"。
- 不同网站账号天然隔离（对话 id 是账号作用域的，不可能出现相同 URL）。

## 二、机器身份：install-time UUID（根因修复）

- 现象：用户观察到 UUID 在变。根因假设：host.py 运行时写 machine.json 失败被
  `except OSError: pass` 静默吞掉 → 每个 host 进程全新 UUID；
  MV3 service worker 反复唤醒拉起新进程，看起来就是"一直在变"。
- 决策：身份签发从 host.py 运行时移到 install.py 安装时。
  - install 仅当 `~/.webai-hands/machine.json` 不存在时生成
    （重装保留——文档流程是 pull 后重跑 install，重装覆盖会轮转身份）；
  - 用户后决定：**直接丢掉 legacy 包袱**，不再认 `~/.config/webai-hands/`
   （无迁移、无回退；远古用户下次安装时身份轮转一次，nag 自愈）；
  - 原子写（tmp + replace）+ 0o600；
  - host.py 只读：读不到就 fail fast（log + 退出），**运行时永不静默签发身份**；
  - 统一 home：native host 永远以 `~/.webai-hands/` 为家
    （machine.json、log/、skill/、history），不再跟着 `__file__` 走；
    repo 里直接跑 host.py 调试需先跑一次 install。
- 边界（诚实说明）：磁盘克隆会带走 UUID（uuid4 防不住，靠"每台机器独立安装"
  流程约束；真要防得上硬件指纹，是另一个取舍）；多 OS 用户按用户隔离（现状语义）。

## 四、线上事故与缺口（2026-10-08，当天实测）

1. WSL 递归扫描占住单 lane 53+ 分钟（AI 写了巨大 timeout，默认 120s 未生效），
   后续命令被 5s 打回 → "排队代替打回"的活验证（但排队不解决队头阻塞）。
2. 页面停止按钮杀不掉 host 里正在跑的进程（无 kill 消息类型）
   → 分支候选：host 侧 kill。
3. 杀掉进程后 lane 仍僵死（管道继承：孤儿进程握着 stdout，Chrome 收不到 EOF，
   onDisconnect 丢失；elapsed 一直涨）→ 复位靠重载扩展 + 刷新页面。
   分支需要：background 看门狗（hostBusy 下 60s 无任何消息→强制重建端口）、
   popup"重建连接"按钮、超时杀进程树（Windows job object）、timeout 上限。
